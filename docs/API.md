# API reference (v1)

Base path: `/api/v1`. Machine-readable: `GET /api/v1/openapi.json` (generated by `npm run openapi`; a test verifies it matches the implemented routes).
Everything is **synthetic**. Results are illustrations, not offers.

## Conventions

- JSON in/out. `Authorization: Bearer <token>` on everything except `/meta`, `/auth/login`, `/auth/demo-users`, `/openapi.json`, `/healthz`.
- **Business outcomes are HTTP 200** with a `status` field. **Contract problems are 4xx** with `{"error":{"code","message","details?"}}`:
  `400 BAD_REQUEST / BAD_JSON`, `401 UNAUTHENTICATED / INVALID_TOKEN / BAD_CREDENTIALS`, `403 FORBIDDEN / FOUR_EYES`, `404 NOT_FOUND / UNKNOWN_PRODUCT`, `409 INVALID_TRANSITION / NOT_EDITABLE / EFFECTIVE_DATE_CONFLICT / …`, `413 BATCH_TOO_LARGE / PAYLOAD_TOO_LARGE`, `422 VALIDATION_FAILED / IMPORT_BLOCKED / WORKBOOK_REJECTED`, `429 TOO_MANY_ATTEMPTS` (failed sign-ins only), `500 INTERNAL` (details logged, never returned).
- Dates are ISO `YYYY-MM-DD`. Money is a JSON number in USD with two decimals.
- Unknown input fields are rejected (`UNKNOWN_FIELD`) so schema drift is noticed.

## Authentication

```bash
curl -s -X POST http://localhost:3000/api/v1/auth/login -H 'content-type: application/json' \
  -d '{"username":"rateguard.client","password":"pilot-api-demo-2026"}'
# -> {"token":"…","user":{"id":"rateguard.client","role":"api_client"},"expiresAt":"…"}
```

Roles: `agent`, `pricing_analyst`, `pricing_approver`, `admin`, `api_client`. Permission matrix: `server/auth.js` (`PERMISSIONS`). Tokens are HMAC-signed, 8 h, demo-only. Cloud mode: [GOOGLE_CLOUD.md](GOOGLE_CLOUD.md).

## Discovery

### `GET /products`
Products with the product-definition version in force today.

### `GET /products/{id}/schema?date=YYYY-MM-DD[&versionId=…]`
The input schema of the **product version in force on `date`** (default today), as UI sections (`sections[].fields[]` / `repeat`, conditional `showIf` / `requiredIf` in the pilot's JSON expression language, cross-field `checks`), plus a standard **`jsonSchema`** (draft 2020-12) for `risk` and `coverages`, and a `requestEnvelope` description. `additionalProperties:false` throughout.

Request conventions: array sections (`drivers`, `vehicles`) live in `risk`; policy-level coverages and discounts live in `coverages`; per-vehicle comprehensive/collision deductibles are fields on each vehicle (documented choice).

### `GET /jurisdictions`
The synthetic demo set (AZ, CA, FL, GA, IL, NY, NC, OR, TX, WA) with ZIP3 plausibility ranges.

### `GET /rating-versions?productId=&state=&status=&scope=`
Version discovery. Each item: `id`, `productId`, `scope` (`{level:"national"}` or `{level:"state",state}`), `versionNumber`, `label`, `effectiveFrom`, `effectiveTo`, `status` (`draft|validated|pending_approval|approved|active|rejected|rolled_back`), `effectiveState` (`scheduled|in_effect|superseded|expired` for active versions), `contentHash`, `basedOn`, `createdBy`, `approvedBy`, `changeTicket`, `demo`, `contentSummary`.
`GET /rating-versions/{id}` returns the full version including `content` (tables, steps, rules, limits). Product versions: `/product-versions[...]`.

### `GET /rating-versions/resolve?productId=&state=&date=`
Which versions a quote would use: product version, national version, state override (or `null`), `effectiveConfigHash` and a plain-language `explanation`.

```json
{"productId":"homeowners","state":"FL","date":"2026-10-15","national":"HO-NAT-v2","stateOverride":"HO-FL-v1",
 "effectiveConfigHash":"1ae3f634df33…","explanation":"HO-NAT-v2 (national) with HO-FL-v1 (FL override), both effective on or before 2026-10-15."}
```

## Quotes

### `POST /quotes` — one synthetic quote

Request (`QuoteRequest`):

| Field | Notes |
| --- | --- |
| `scenarioId` | optional, echoed back; generated (`adhoc-…`) if absent |
| `productId` | `personal-auto \| homeowners \| commercial-property \| bop` |
| `state` | demo state code |
| `transactionType` | `NEW_BUSINESS` (default) `\| RENEWAL \| ENDORSEMENT` |
| `effectiveDate` | transaction effective date (selects versions; for `ENDORSEMENT`, versions come from `policyEffectiveDate`) |
| `policyEffectiveDate` | optional; required in spirit for `ENDORSEMENT` |
| `risk`, `coverages` | per the product schema |
| `endorsement` | `{priorRisk, priorCoverages?}` — required for `ENDORSEMENT` |
| `priorTermPremium` | `RENEWAL` only; enables the renewal rate-change cap |
| `ratingVersionIds` | `{national?, state?}` pin versions, including drafts. **pricing/API roles only** (`403` otherwise). `state:null` = no state override |
| `productVersionId` | pin a product version (same permission) |
| `options.trace` | default `true` |

`?persist=true` stores an immutable quote record (`quoteId`) and writes an audit entry; default is stateless.

`status` values and what is present:

| status | meaning | `premium` | other |
| --- | --- | --- | --- |
| `QUOTED` | eligible and rated | yes | `eligibility.reasons` empty |
| `REFERRED` | a referral rule triggered | **no** | `eligibility.reasons[]` |
| `DECLINED` | a decline rule triggered | **no** | reasons |
| `INFO_REQUIRED` | more information needed (e.g. FL coastal flat wind deductible) | **no** | reasons |
| `INVALID` | input validation failed | no | `validation.errors[]` `{path, code, message}` |
| `RATING_ERROR` | configuration cannot rate this risk (`NO_RATE_FOUND`, `AMBIGUOUS_RATE`, `NO_APPLICABLE_VERSION`, …) | no | `error{code,message,details}` |

`resultHash` is a deterministic SHA-256 over outcome + versions (excluding ids/timestamps): identical request + identical versions ⇒ identical hash.

`ENDORSEMENT` adds `endorsement`: `{computed, priorPremium, newPremium, annualPremiumChange, policyExpirationDate, termDays, daysRemaining, proratedChange, method}`. Both risks are rated with versions in force on `policyEffectiveDate`.

`INVALID` example:

```json
{"status":"INVALID","errors":[
 {"path":"risk.zip","code":"ZIP_STATE","message":"ZIP code 90210 is outside the ZIP ranges used for AZ in this demo."},
 {"path":"risk.roof_year","code":"CROSS_FIELD","message":"Roof year cannot be earlier than the year built."}]}
```

### `POST /quotes/batch`
`{ "defaults": {…merged under each scenario…}, "scenarios": [ QuoteRequest, … ≤ 200 ], "options": { "trace": false } }`.
Synchronous; each item is independent. A malformed item becomes `{"scenarioId","status":"REQUEST_ERROR","error":{…}}` instead of failing the batch. Over 200 ⇒ `413`.

```json
{"batchId":"B-8c93f9d38484","count":2,"summary":{"QUOTED":1,"INVALID":1},
 "results":[{"scenarioId":"a","status":"QUOTED","total":1606.83},{"scenarioId":"b","status":"INVALID"}]}
```
(Each result is a full `QuoteResult`; shortened here.) Pub/Sub-based async batches are **not** implemented (not needed at this scale).

### `POST /validate-submission`
Same body as `/quotes`; returns `{valid, status, errors, warnings, eligibility, versions}` without a premium.

### `GET /quotes/{id}`
A stored (immutable) quote created with `?persist=true` or via a submission.

## Validation of a draft rating version

### `POST /rating-versions/validate`
Body: `{productId, scope, effectiveFrom, content}` — validated **without storing**. Returns `{valid, errors[], warnings[], info[], smoke, impact, candidateHash, note}`.
### `POST /rating-versions/{id}/validate`
Stored version. Pricing editors persist the result (status → `validated`/`draft`); other roles (e.g. `api_client`) get a read-only report (`persisted:false`).

What the gate checks: step ids/ops, expression nodes (closed vocabulary), input references against the product schema, variables/params defined before use, table structure, **range gaps and overlaps**, duplicate keys, **plausible value bounds** (e.g. factors 0.2–5), **option completeness** (every product option has a rate row), limits/rounding sanity, state-override targets, then a **smoke run** over ~25 scenarios (no rating failures, positive premiums) and an **impact summary** vs the version it replaces.
What it cannot do: prove a plausible number is the *intended* number. The seeded "silent defect" passes by design.

## Workbench lifecycle (roles in parentheses)

`POST /rating-versions` (analyst/admin) create draft · `PUT /rating-versions/{id}` edit · `POST …/{id}/submit | withdraw` · `…/approve | reject` (approver/admin; **not the creator/submitter**) · `…/promote` (approver/admin; re-validates; blocks effective-date conflicts) · `…/rollback` (approver/admin; reason required) · `GET /rating-versions/{a}/diff/{b}` · `GET /rating-versions/{id}/export.xlsx` · `POST /demo/drafts`. Product versions mirror these under `/product-versions`.

## Submissions (agent and up)

`GET|POST /submissions`, `GET|PUT|DELETE /submissions/{id}`, `POST /submissions/{id}/rate` (stores an immutable quote), `GET /submissions/{id}/quotes`, `POST /submissions/{id}/bind-simulated`, `POST /submissions/{id}/scenarios` (`{type: RENEWAL|ENDORSEMENT, effectiveDate}`).

## XLSX, test tooling, feedback, audit

See [XLSX_PROFILE.md](XLSX_PROFILE.md) for `/workbooks/*`. `POST /test-tools/compare` (pilot test tooling — compares two *pilot* configurations; **not** RateGuard assurance). `/feedback*`, `/audit`, `/audit/verify`, `POST /admin/reset` (admin, `{"confirm":"RESET"}`).

## Limits

JSON bodies ≤ 2 MB; uploads ≤ 6 MB (workbooks ≤ 5 MB); batch ≤ 200 scenarios; expressions ≤ 400 nodes / depth 24.
